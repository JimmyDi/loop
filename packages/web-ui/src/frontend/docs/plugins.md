# Plugins settings

Open **Settings → Integrations → Plugins** to manage MCP servers. The page contains a server count, case-insensitive search, transport, current connection status and discovered tool count. The gear edits configuration; the switch persists enabled state; failed connections offer Retry. The header says Manage MCPs. The wider Plugins panel uses the same 18px, medium-weight heading and 13px control text as other Settings sections, with a selected MCPs capsule and a pill search field with a search icon on one toolbar without a divider. Server rows have no card borders; transport icons, server names, status details and blue enabled switches share a consistent alignment. Availability guidance appears below the list. The compact white pill Add button uses a 34px minimum height and opens a narrow dropdown with Add MCP server; pointer selection and Enter open the configuration form, Escape closes the menu and restores trigger focus, and clicking outside or pressing Tab dismisses it. Transient focus changes during pointer activation do not remove the item before its click opens the form.

On narrow screens, the navigation becomes more compact, the search field shrinks within its toolbar and server actions wrap below their details. Configuration fields stay inside the panel while long forms scroll vertically.

## Adding and editing

The configuration form replaces only the server list: the Plugins heading, Manage MCPs description, count and search toolbar remain visible. Add stays visible but is disabled while a draft is open. Back restores the list and its search. Provide a display name and select STDIO or Streamable HTTP. Each transport retains its own draft when switching; Save sends only the selected transport. The form uses a compact 16px heading, 12px labels, input and button text, and 11px helper text. Name and the connection type share one rounded card. Name occupies the upper section; a full-width divider separates the lower row, which places Type on the left and compact STDIO/Streamable HTTP choices on the right, with a filled selected choice and muted inactive text. Other fields use rounded inputs and 18px section spacing. Errors preserve the form. Back returns to the server list; Delete asks for confirmation before removal.

STDIO fields are launch command, separate argument rows, literal environment key/value rows, environment-variable passthrough names and an optional absolute working directory. HTTP fields are URL, bearer-token environment-variable name, literal header rows and header keys mapped to environment-variable names. Each repeatable field starts with one empty input row, including when the saved list is empty or its final row is removed. Add appends another row. Unused optional key/value and environment-reference rows are omitted on save; saved write-only values and intentionally empty command arguments are retained. Add/remove row controls operate independently. Each row uses a muted outline trash icon for deletion, with a localized accessible label.

Literal environment/header values are password inputs and write-only after saving. Leave a saved value empty to keep it, replace it to update, or remove the row to delete. Changing the connection target requires re-entering retained values. Environment references contain variable names, not secret values; they refer to the environment in which the backend was started.

Save persists locally and starts connection asynchronously. Saving and verification preserve the form’s current scroll position. A translucent overlay covers its fields and actions immediately on Save, with a ring spinner and nearby localized saving, queued, connecting or refreshing guidance. The indicator stays visible within the scrollable panel. The helper copy is a brief Please wait a moment in the selected language, without download, timeout or background-operation details. Loop reports actual lifecycle stages without guessing download percentages. Once the connection is ready, the form closes and returns to the MCP list. Saving a disabled server also returns to the list after persistence. Persistence or connection failure removes the overlay and keeps the form open at the current position with a safe error. The Plugins header, navigation and Back remain outside the overlay; Back is available after persistence. Fields and Save are disabled during this verification, while Back remains available after persistence. STDIO saves allow up to two minutes for first-launch downloads; HTTP saves, normal startup, enabling and list Retry keep their short deadlines. Failure retains the saved configuration and enables editing or Save again; subsequent saves update the existing server instead of creating a duplicate. Successfully saved literal values are cleared from inputs and marked saved for write-only retention. Connecting servers do not delay startup, typing, chat requests or built-in tools. Connected tools become available on the next user prompt. Queued means waiting for a discovery slot; Connecting performs initialization and discovery; Refreshing tools updates a changed catalog on the existing connection. A connection error does not interrupt unrelated sessions; the row gives a safe explanation and recovery hint, and Retry starts fresh discovery. The page refreshes status every second during queued, connecting or refreshing states, otherwise every three seconds while visible with enabled servers.

## Storage, approvals and limits

Configuration lives outside the project in `<agentDir>/mcp.json`, with private file permissions and no browser persistence. Literal values are plaintext on disk; prefer environment references for credentials. STDIO launches the configured process with host access. Chat execution rows and completed batch summaries display the server name and original full tool name, for example Example MCP · list_directory, instead of hashed internal identifiers. New results retain this presentation label in history. Legacy results can use a ready catalog to resolve names; otherwise they retain the internal identifier. MCP calls follow session permissions: Full access calls tools without confirmation, while Read only and Workspace write require approval unless a live tool/session grant exists. Plugins has no separate permission settings. Server risk declarations do not bypass approval or enforce access boundaries. Calls requiring approval show the server, tool and exact arguments, with Deny, Allow once and Allow this tool for this session. The session option covers that exact tool with any arguments until its live session or catalog lifetime ends. Configuration changes, disabling, reconnecting and catalog refresh revoke grants; display-name-only edits preserve them. Session grants are not saved or shared between sessions. Cancelling a call may not undo changes already made by the external server.

Plugins currently manages MCP servers only. Package installation, OAuth, plugin bundles, skill management, MCP Apps, resources and prompts are not implemented. A changed server tool catalog refreshes automatically; stale tools and approvals are invalidated immediately. Failed refreshes offer Retry. Automatic reconnection is not implemented. See [core MCP behavior](../../../../coding-agent/src/docs/mcp.md) and [HTTP endpoints](../../backend/docs/mcp.md).
